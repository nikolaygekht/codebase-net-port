# The VFP oracle

A second offline oracle, run in a **Visual FoxPro 9 VM**. It produces the corpus files the C
generator beside it *cannot* — because that generator is CodeBase, and the questions here are about
what CodeBase does not do.

Decided in **ADR-44**, which supersedes ADR-04's "no VFP VM, for now". The rules that bind this
directory are there; this file is how to run it.

## Why it exists

CodeBase has 35 named functions and **no arithmetic at all** (`EXPRESSIONS.md` §5.1). `ABS`, `INT`,
`ROUND`, `MOD`, `MIN`, `MAX`, `SQRT`, `SIGN`, `LEN`, `AT`, `ASC`, `LOWER` and `REPLICATE` are refused
with `e4unrecFunction` (−470) — the thirteen `[vfp-only]` rows of `CDXEXPR.expr.dump.txt`. Visual
FoxPro has them, and **a CDX that VFP writes may legitimately index by one**, so the port must read
such a tag (ADR-43). Nothing generated by CodeBase can gate that.

## Running it

In the VM, with this directory reachable:

```foxpro
DO vfpfunc.prg                          && output lands in .\out\
DO vfpfunc.prg WITH "D:\some\where"     && or wherever you say
```

Then, on the Windows side:

```bat
copy-vfp-corpus.bat        :: out -> ..\..\net\corpus\vfp
```

Nothing in the .NET build runs any of this. The **committed files are the artifact** (ADR-01); the
script is checked in for provenance and so the next run is the same run.

## What it produces

| File | What it is |
|---|---|
| `VFPFUNC.DBF` + `.cdx` | 16 records, **18 tags** — one per VFP-only function, plus four shared-name probes. The tag headers carry VFP's own **key length** and the leaves its own **key bytes** |
| `VFPFVAL.DBF` | one record per constant expression, the result stored in a field **of its own type** |
| `VFPFUNC.vfp.dump.txt`, `VFPFVAL.vfp.dump.txt` | what VFP says about both, for review and diff |

**The `.DBF`/`.cdx` files are the oracle, not the text dumps.** A double written to a `B` field is
the bits VFP computed; printing it as decimal text would hide the low bits the key transform depends
on. The dumps say so wherever a number in them is display-only.

`VFPFVAL`'s `RESLEN` carries the true length of a character result, because the `C(80)` field pads
and a trailing blank would otherwise be indistinguishable from padding.

## What the first run settled

Run on 2026-08-29; output in [`net/corpus/vfp/`](../../net/corpus/README.md#vfp-produced-cases--vfp).
The durable form of all of this is in `specs/EXPRESSIONS.md` §9.1 and §7.3 and `specs/CDX-FORMAT.md`
§3 — this list is what to look at first when re-reading the dumps.

**Key length is not the risk ADR-43 thought it was.** Read out of the tag headers VFP wrote: every
numeric-returning function keys to **8**; `LOWER`, `PROPER`, `TRIM` and `UPPER` over a `C(20)` key to
**20**; `REPLICATE(k_text,2)` to **40**; `STR(k_num,12,3)` to **12**. VFP sizes by result type, by
operand width, by the multiplier and by the width argument respectively — the same rule the port
would compute.

**`T_STRTRN` is the finding it was meant to be, and the answer is not "refuses".** VFP sizes
`STRTRAN(k_text,"A","BB")` at the **operand's** width, 20, writes the tag header, and then fails on
the first record whose result does not fit — the 20-character row yields 21 bytes. So the failure is
at *build* time, not parse time, and **the refused tag's three blocks stay in the file**, orphaned
but well-formed, reachable only if you scan for header blocks instead of reading the tag directory.
`VFPFUNC.cdx` is eighteen tag groups and seventeen live tags for exactly this reason.

**`T_VTRIM` did not diverge in length.** `TRIM(k_text)` keys to 20, the source width — the same as
CodeBase's NUL-padded source width. The divergence that would have broken *reading* a VFP-written
tag is not there.

**`STR` rounding agrees**, closing ADR-43's own open question with no divergence: VFP returns `3`,
`-3`, `0.13` and `0.14` for the four midpoint probes, matching the C library's half-away-from-zero
on the decimal digits.

**`T_UPPER`, the control, agrees** — so the harness is sound and the findings above are VFP's, not
the script's.

**Two things nobody was looking for.** VFP **lower-cases identifiers** in the stored expression text
(`INDEX ON ABS(K_NUM)` stores `ABS(k_num)`; tag names in the directory too) while `KEY()` and
`TAG()` hand them back upper-cased. And `STRZERO` **is not a VFP function at all** — VFP parses it
as a UDF call and reports `File 'strzero.prg' does not exist`.

**Two divergences that are now decided rather than suspected** (ADR-45):

- **Prefix `=`.** VFP compares to the end of the **right** operand, so `"AAAA" = "AAA"` is true and
  `"AAA" = "AAAA"` is false; CodeBase's common-prefix rule makes both true. This is the **reverse**
  of the direction Sequiter's own comment gives at `e4parse.c:59-62`, which three of our documents
  had repeated on its authority. The port replicates CodeBase.
- **The century pivot.** VFP has a rollover (`yy < nYear` → `nCentury + 1`, inclusive at `nYear`)
  where CodeBase has none at all (`year / 100` off the clock). On a 2026 clock `CTOD("01/15/99")` is
  **2099 in CodeBase and 1999 in VFP**. VFP's default rollover is the machine's year + 50, mod 100,
  which is why the script now pins `SET CENTURY TO 19 ROLLOVER 29` — unpinned, these rows change
  every January.

**One thing the run does not answer, and it is a scope call rather than a bug.** The VM's code page
is **1251**, so `VFPFUNC.DBF` carries mark `0xC9` where `CDXEXPR.DBF`, the table it mirrors, carries
`0x00`. Ordering is unaffected (`MACHINE` is a byte compare), but `LOWER`/`UPPER`/`PROPER` above
`0x7F` are code-page behaviour, and record 16 is the only row that exercises it.

## Determinism, and the two ways these files differ from the C corpus

Every `SET` the output depends on is pinned at the top of the script and recorded in the dump
header: `COLLATE` (key bytes — **`MACHINE`**, deliberately, so the first run needs no weight table),
`CENTURY`, `DATE`, `EXACT`, `NULL`, `DECIMALS`, and `CPCURRENT()`. Two of them are also varied on
purpose, in the `exact-on` and `century-on` groups.

- **The DBF header date stamp is frozen** to `26-01-01` by the script, exactly as `util.cpp` freezes
  it for the C corpus (ADR-07). It is the only place the script alters what VFP wrote.
- **The trailing `0x1A` is kept.** VFP writes one on a `0x30` file and CodeBase does not
  (`DBF-FORMAT.md`); that byte is a reader-tolerance case the corpus never had, so it stays.
- The `.cdx` tag-directory **version counter** (big-endian, file offset 8) is VFP's own and may move
  between runs. `PORTING-PLAN.md` §8 already lists it as assert-and-mask.

## What is deliberately not here

The corpus's own generator stays the authority for everything CodeBase can produce. In particular
this directory does **not** try to answer: the parse-rejection surface and its error codes, the
compiled node arrays, `0x31` tables, `keyLen > 240`, CDX block sizes other than 512, the `'7'`
datetime, or compressed memo (`c4compress` is a CodeBase extension with no VFP counterpart — ADR-23
stays open regardless of this VM).

The other runs ADR-44 authorises — code-page marks beyond CodeBase's five constants, a VFP 9 `0x32`
table with a memo, `V`/`Q`/`W` fields, native auto-increment, a DBC backlink, an insert-and-split
tree with a non-empty free list — are separate scripts, each with its own case. They are not written
yet.
