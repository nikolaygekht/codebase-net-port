# The VFP oracle

A second offline oracle, run in a **Visual FoxPro 9 VM**. It produces the corpus files the C
generator beside it *cannot* — because that generator is CodeBase, and the questions here are about
what CodeBase does not do.

Decided in **ADR-44**, which supersedes ADR-04's "no VFP VM, for now". The rules that bind this
directory are there; this file is how to run it.

## Why it exists

CodeBase has 35 named functions and **no arithmetic at all** (`EXPRESSIONS.md` §5.1). `ABS`, `INT`,
`ROUND`, `MOD`, `MIN`, `MAX`, `SQRT`, `SIGN`, `LEN`, `AT`, `ASC`, `LOWER` and `REPLICATE` are refused
with `e4unrecFunction` (−470) — the thirteen `[vfp-only]` rows of `CDXEXPR.expr.dump.txt`. Visual
FoxPro has them, and **a CDX that VFP writes may legitimately index by one**, so the port must read
such a tag (ADR-43). Nothing generated by CodeBase can gate that.

## Running it

**Unattended, from the host** (step 013, 7a-6), when the VM runs under VMware Workstation:

```powershell
run-in-vm.ps1                                  # vfpfunc.prg, 600 s timeout
run-in-vm.ps1 -Script other.prg -TimeoutSeconds 120
run-in-vm.ps1 -Script vfpgen.prg -CodePage 1250 -ScriptArgs '"C1 E1"'
```

`-CodePage` runs VFP under another current code page, through a `config.fpw` with `CODEPAGE=`
copied into the job folder and passed by `-c`. That file replaces the one VFP would otherwise read,
so it also clears `_STARTUP` — left set, VFP starts its Task Pane, and the Task Pane's "Locate /
Create Task Pane Manager Folders" dialog waits for a click nobody gives. `-ScriptArgs` adds VFP
expressions after the output directory in the script's `DO ... WITH`.

The VM must already be running with its user logged in — VFP is a GUI program, and `vmrun
-interactive` runs it in that session; the script never starts or stops the VM. It copies the
script into the guest with a generated wrapper that writes `OK` or the untrapped error into
`done.txt` and quits, so an error cannot leave a dialog nobody sees; a run past the timeout has
`vfp9.exe` killed in the guest. Output lands in `.\out\`, emptied first. Settings come from the
environment and never from the repository: `VFP_VM_VMX`, `VFP_VM_USER`, `VFP_VM_PASS` (the guest's
logged-in user), and optionally `VFP_VM_EXE` and `VMRUN`.

**Or by hand**, in the VM, with this directory reachable:

```foxpro
DO vfpfunc.prg                          && output lands in .\out\
DO vfpfunc.prg WITH "D:\some\where"     && or wherever you say
```

Then, on the Windows side:

```bat
copy-vfp-corpus.bat        :: out -> ..\..\net\corpus\vfp
```

Nothing in the .NET build runs any of this. The **committed files are the artifact** (ADR-01); the
script is checked in for provenance and so the next run is the same run.

## What it produces

| File | What it is |
|---|---|
| `VFPFUNC.DBF` + `.cdx` | 16 records, **18 tags** — one per VFP-only function, plus four shared-name probes. The tag headers carry VFP's own **key length** and the leaves its own **key bytes** |
| `VFPFVAL.DBF` | one record per constant expression, the result stored in a field **of its own type** |
| `VFPFUNC.vfp.dump.txt`, `VFPFVAL.vfp.dump.txt` | what VFP says about both, for review and diff |
| `VFPTIME.DBF` + `.cdx`, `VFPTIME.vfp.dump.txt` | from `vfptime.prg`: 100 422 datetimes and the tag VFP keyed them into; the dump is provenance only (settings, per-day counts, the tag) and carries no run date |
| `VFPG<cp>.DBF` + `.CDX`, `VFPG<cp>.vfp.dump.txt` | from `vfpgen.prg`, one per code page VFP has GENERAL on (437, 620, 850, 852, 857, 861, 865, 895, 1250, 1252, 1254, 10000, 10029): each byte alone, each byte beside two partners, runs of twelve, 787 records under one GENERAL tag. The weights are recovered from the keys |
| `VFP<NAM><cp>.DBF` + `.CDX`, `.vfp.dump.txt` | from `vfpgen.prg` with a collation's name, `<NAM>` its first three letters: the 51 pairs VFP builds a named collation on, the same shape as `VFPG` plus rows aimed at the contractions. The weights and sequences are recovered from the keys |
| `VFPPROP.DBF` + `.CDX`, `VFPPROP.vfp.dump.txt` | from `vfpprop.prg`: 292 values of a nullable `C(30)` — 36 named probes, then a letter, each of the 256 bytes and a letter — under one tag, `PROPER(K)`. The keys are what VFP takes for a word |
| `VFPBAND.DBF` + `.CDX`, `VFPBAND.vfp.dump.txt` | from `vfpband.prg`: six records with nulls in a nullable `N` and `C` field, and one tag per VFP-only function over them — VFP's keys for null results. The dump **is** the oracle for what has no bytes: which probes raise, with VFP's error number and message, what a null operand answers, and which operands `IIF`/`AND`/`OR` evaluate |

**The `.DBF`/`.cdx` files are the oracle, not the text dumps.** A double written to a `B` field is
the bits VFP computed; printing it as decimal text would hide the low bits the key transform depends
on. The dumps say so wherever a number in them is display-only.

`VFPFVAL`'s `RESLEN` carries the true length of a character result, because the `C(80)` field pads
and a trailing blank would otherwise be indistinguishable from padding.

## What the first run settled

Run on 2026-08-29; output in [`net/corpus/vfp/`](../../net/corpus/README.md#vfp-produced-cases--vfp).
The durable form of all of this is in `specs/EXPRESSIONS.md` §9.1 and §7.3 and `specs/CDX-FORMAT.md`
§3 — this list is what to look at first when re-reading the dumps.

**Key length is not the risk ADR-43 thought it was.** Read out of the tag headers VFP wrote: every
numeric-returning function keys to **8**; `LOWER`, `PROPER`, `TRIM` and `UPPER` over a `C(20)` key to
**20**; `REPLICATE(k_text,2)` to **40**; `STR(k_num,12,3)` to **12**. VFP sizes by result type, by
operand width, by the multiplier and by the width argument respectively — the same rule the port
would compute.

**`T_STRTRN` is the finding it was meant to be, and the answer is not "refuses".** VFP sizes
`STRTRAN(k_text,"A","BB")` at the **operand's** width, 20, writes the tag header, and then fails on
the first record whose result does not fit — the 20-character row yields 21 bytes. So the failure is
at *build* time, not parse time, and **the refused tag's three blocks stay in the file**, orphaned
but well-formed, reachable only if you scan for header blocks instead of reading the tag directory.
`VFPFUNC.cdx` is eighteen tag groups and seventeen live tags for exactly this reason.

**`T_VTRIM` did not diverge in length.** `TRIM(k_text)` keys to 20, the source width — the same as
CodeBase's NUL-padded source width. The divergence that would have broken *reading* a VFP-written
tag is not there.

**`STR` rounding agrees**, closing ADR-43's own open question with no divergence: VFP returns `3`,
`-3`, `0.13` and `0.14` for the four midpoint probes, matching the C library's half-away-from-zero
on the decimal digits.

**`T_UPPER`, the control, agrees** — so the harness is sound and the findings above are VFP's, not
the script's.

**Two things nobody was looking for.** VFP **lower-cases identifiers** in the stored expression text
(`INDEX ON ABS(K_NUM)` stores `ABS(k_num)`; tag names in the directory too) while `KEY()` and
`TAG()` hand them back upper-cased. And `STRZERO` **is not a VFP function at all** — VFP parses it
as a UDF call and reports `File 'strzero.prg' does not exist`.

**Two divergences that are now decided rather than suspected** (ADR-45):

- **Prefix `=`.** VFP compares to the end of the **right** operand, so `"AAAA" = "AAA"` is true and
  `"AAA" = "AAAA"` is false; CodeBase's common-prefix rule makes both true. This is the **reverse**
  of the direction Sequiter's own comment gives at `e4parse.c:59-62`, which three of our documents
  had repeated on its authority. The port replicates CodeBase.
- **The century pivot.** VFP has a rollover (`yy < nYear` → `nCentury + 1`, inclusive at `nYear`)
  where CodeBase has none at all (`year / 100` off the clock). On a 2026 clock `CTOD("01/15/99")` is
  **2099 in CodeBase and 1999 in VFP**. VFP's default rollover is the machine's year + 50, mod 100,
  which is why the script now pins `SET CENTURY TO 19 ROLLOVER 29` — unpinned, these rows change
  every January.

**One thing the run does not answer, and it is a scope call rather than a bug.** The VM's code page
is **1251**, so `VFPFUNC.DBF` carries mark `0xC9` where `CDXEXPR.DBF`, the table it mirrors, carries
`0x00`. Ordering is unaffected (`MACHINE` is a byte compare), but `LOWER`/`UPPER`/`PROPER` above
`0x7F` are code-page behaviour, and record 16 is the only row that exercises it.

## What the second run settled

Run on 2026-11-14, the first through `run-in-vm.ps1`. `VFPFUNC.DBF` and `VFPFUNC.CDX` came back
**byte-identical** to the first run's — the `.cdx` version counter did not move either — and
`VFPFVAL.DBF` changed in records 65, 66 and 77 only: the three `CTOD` rows rewritten after the first
run. They now straddle the pinned `ROLLOVER 29`, so one dump proves the rule that took two runs to
see: `CTOD("01/15/28")` is **2028**, `CTOD("01/15/29")` is **1929** — below the rollover the next
century, at it this one, the boundary inclusive (`specs/EXPRESSIONS.md` §7.3).

## What `vfptime.prg` settled

Run on 2026-11-14 through `run-in-vm.ps1`; output `VFPTIME.DBF` + `.CDX` (step 013, 7a-7). One `T`
field, one ascending tag, 100 422 records: every second of 2000-01-01, and every 37th second plus
the last of six days chosen so all three binades of the Julian day are sampled (VFP's `DATE()`
refuses year 1, so the lowest is 0100). The durable form is `specs/KEY-COLLATION.md` §2.8.

**VFP's datetime key, deciphered.** `fl(fl(day × 86400 + s) × fl(1/86400))`: the moment in seconds
times the double nearest 1/86400. It reproduces all 100 422 keys, and every key of CodeBase's own
`CDXTIME`. CodeBase's `flags4dateTimeFlags` bitmap is this formula sampled around 2000: exact on
2000-01-01, one unit off on 7 and 3 of the sampled seconds of 1900 and 2026, and on about half of
them below 2²¹ and above 2²². The port now keys `T` by the formula (ADR-78).

**VFP stores a datetime one millisecond short** about half the time — `DTOT(d) + n` is computed as a
double of days and truncated into the field. 43 136 of the 86 400 seconds of 2000-01-01 read
`…999`. The port reads a `T` field to the second (ADR-79).

## What `vfpband.prg` settled

Run on 2026-11-15 through `run-in-vm.ps1` (step 013, 7a-9). The durable form is `specs/EXPRESSIONS.md`
§5.2; the decisions are ADR-81 and ADR-82.

**`MOD` by zero and `SQRT` below zero raise** — errors 1307 and 61 — which step 010 had recorded
without a witness. `1/0` does not raise: VFP overflows, and the port keeps CodeBase's zero (ADR-50).

**VFP is lazy where the port was not.** `IIF` evaluates only the branch it chose; `AND`/`OR` stop at
the first operand that decides, left to right. So `COUNT FOR K >= 0 AND SQRT(K) > 1` counts, and
`INDEX ON IIF(K < 0, 0, SQRT(K))` builds, where the unguarded forms raise — and an unguarded
`INDEX ON` leaves **no tag at all**.

**A null operand makes every one of the thirteen answer null**, in every argument position — except
that `MOD` tests its divisor first, so `MOD(N_, 0)` raises over a null `N_`. VFP's untyped `.NULL.`
literal differs (`MOD(.NULL., 0)` is `.NULL.`), which is why the probes use typed nulls from fields.

Two probes in the dump answer nothing: `ATN2(SQRT(-0), -1)` shows that VFP's `-0` literal is a
positive zero, so the sign of `SQRT(-0)` stays unknown; and `1/0`'s value prints as asterisks.

## What `vfpgen.prg` settled

Run on 2026-11-15 under each code page the port knows (step 013, 7a-13); decision ADR-86, durable
form `specs/KEY-COLLATION.md` §4.1.

**VFP has GENERAL on thirteen code pages**: 437, 620, 850, 852, 857, 861, 865, 895, 1250, 1252,
1254, 10000, 10029. On 737, 866, 874, 1251, 1253, 10006 and 10007 it refuses one ("Collating
sequence 'GENERAL' is not found", error 1915); 1255 and 1256 it would not run under, staying on the
VM's 1251. The multi-byte pages were not tried.

**Two passes per page.** The first, with no partners, shows which bytes carry a nonzero tail; two of
them become the second pass's partners, because a byte's tail of zero and no tail at all look the
same in its own key and differ once a partner's tail follows. The second pass is the corpus.

**On cp437 and cp1252 VFP's keys are CodeBase's** — CodeBase's tables rebuild every one. **On cp850
they are not**, in thorn alone: VFP expands `þ`/`Þ` (0xE7/0xE8) to the heads of T and H, CodeBase's
table gives the head of T and a tail of 0x69, and its cp850 expansions have no TH.

**RUSSIAN, the first named collation** (7a-15, ADR-87). `vfpgen.prg` takes a collation's name as its
third argument and, as its fourth, `.T.` for every letter (`ISALPHA()`) beside every letter — the only
place a contraction would show:

```powershell
run-in-vm.ps1 -Script vfpgen.prg -CodePage 1251 -ScriptArgs '"A5 B4", "RUSSIAN", .T.'
```

The tables are `VFPRUS<cp>`. On cp1251 and cp866: GENERAL's layout, case folded, `Ё` its own head
after `Е`, no expansion, tails only on cp1251's `Ґ`/`ґ` (so cp866 needs no partner), and **no
contraction**: every one of 21 316 letter pairs on cp1251 and 15 376 on cp866 rebuilt from the
letters' weights. The corpus holds the runs without the pairs, which were 800 KB to prove that once.

**The other named collations** (7a-15, ADR-88). `vfpcoll.prg` tries each of VFP's fifteen collation
names under the code page it runs on and writes `VFPCOLL<cp>.txt`, built or the error:

```powershell
run-in-vm.ps1 -Script vfpcoll.prg -CodePage 1250
```

Over every page the port knows, VFP builds a named collation on **51 pairs**: CZECH and SLOVAK on 852,
895, 1250, 10029; DUTCH and SPANISH and UNIQWT on 437, 850, 1252, 10000; GERMAN on 437, 1252, 10000;
GREEK on 737, 1253, 10006; HUNGARY on 852, 1250; ICELAND on 437, 850, 861, 1252; NORDAN and SWEFIN
on 437, 850, 865, 1252, 10000; POLISH on 620, 852, 1250, 10029; RUSSIAN on 866, 1251, 10007;
TURKISH on 857, 1254. Everywhere else, error 1915.

A first pass with letter pairs found the **contractions** — CZECH/SLOVAK `CH`, SPANISH `CH` `LL`,
NORDAN `AA`, HUNGARY `CS DZ GY LY NY SZ TY ZS` and `DZS`, any case — and no others among letters; and
three expansions no two characters spell (SWEFIN `Æ`/`æ`, DUTCH `ÿ` on cp10000, UNIQWT `ß` on cp850).
The final pass, the corpus, drops the pairs and passes the rows that matter as a fifth argument,
hex strings separated by blanks — each contraction alone, beside each partner, doubled, and with its
first byte doubled:

```powershell
run-in-vm.ps1 -Script vfpgen.prg -CodePage 1250 -ScriptArgs '"43 63", "CZECH", .F., "4348 434843 434863 ..."'
```

**VFP refuses a string literal over 255 characters** ("Command contains unrecognized phrase/keyword",
error 36), and SPANISH's and HUNGARY's rows run longer: pass them as several literals joined with `+`.

## What `vfpprop.prg` settled

Run on 2026-11-15 (step 013, 7a-10); durable form `specs/EXPRESSIONS.md` §5.2, decision ADR-83.

**`PROPER` begins a word after white space and nothing else.** Of the 256 bytes between two letters,
on the VM's code page 1251, exactly `0x09`–`0x0D`, `0x20` and `0xA0` upper-case the letter after
them: `isspace` plus the no-break space. Apostrophe, hyphen, full stop, digits, brackets, `_`, `/`,
`0x00`, the dashes and the guillemets do not — `O'neil`, `Mary-jane`, `Mr.smith`, `1st Place`,
`(paren) Word`, `Mcdonald`. Everything not upper-cased is lowered, through the whole of 1251
(`ИВАН ПЕТРОВ` is `Иван Петров`; `Ђ`, `Ј`, `Ґ`, `Ѕ`, `Ё` lower too).

## Determinism, and the two ways these files differ from the C corpus

Every `SET` the output depends on is pinned at the top of the script and recorded in the dump
header: `COLLATE` (key bytes — **`MACHINE`**, deliberately, so the first run needs no weight table),
`CENTURY`, `DATE`, `EXACT`, `NULL`, `DECIMALS`, and `CPCURRENT()`. Two of them are also varied on
purpose, in the `exact-on` and `century-on` groups.

- **The DBF header date stamp is frozen** to `26-01-01` by the script, exactly as `util.cpp` freezes
  it for the C corpus (ADR-07). It is the only place the script alters what VFP wrote.
- **The trailing `0x1A` is kept.** VFP writes one on a `0x30` file and CodeBase does not
  (`DBF-FORMAT.md`); that byte is a reader-tolerance case the corpus never had, so it stays.
- The `.cdx` tag-directory **version counter** (big-endian, file offset 8) is VFP's own and may move
  between runs. `PORTING-PLAN.md` §8 already lists it as assert-and-mask.

## What is deliberately not here

The corpus's own generator stays the authority for everything CodeBase can produce. In particular
this directory does **not** try to answer: the parse-rejection surface and its error codes, the
compiled node arrays, `0x31` tables, `keyLen > 240`, CDX block sizes other than 512, the `'7'`
datetime, or compressed memo (`c4compress` is a CodeBase extension with no VFP counterpart; the
CodeBase generator's `CMPMEMO` covers it — ADR-55).

The other runs ADR-44 authorises — code-page marks beyond CodeBase's five constants, a VFP 9 `0x32`
table with a memo, `V`/`Q`/`W` fields, native auto-increment, a DBC backlink, an insert-and-split
tree with a non-empty free list — are separate scripts, each with its own case. They are not written
yet.
